Improvement suggestions

Eighteen specific, owner-assigned suggestions with priorities, and a review workflow so a path can be chosen before anything changes.

Suggestions, and how to choose between them

The household asked for a dedicated section where suggestions can be reviewed and a path chosen before anything is implemented. This is that section. Each suggestion carries a priority, an owner, an effort estimate and the specific question it closes, so a reviewer can sort by what actually unblocks the decision rather than by what is interesting.

How to use this page

Sort by Priority. Do the seven HIGH items first — five of them cost under $1,000 combined and close the questions that currently make the recommendation provisional. Everything marked Site feature or Model improves the analysis but does not unblock it. Nothing here should be implemented before S1, S2, S5, S6 and S8.

Site improvements specifically for decision-making

Separate from the analysis questions, these are improvements to the site itself, in the order I would make them.

  1. A dependency-free what-if calculator. Sliders for value, tax rate, maintenance, rent and growth, recomputing net worth live in the browser. No server, no analytics, no third-party script. This is the single most valuable addition, because it lets the household see the sensitivity for themselves instead of trusting a table.
  2. Charge market rent on the sell path. The model credits imputed rent to ownership but does not charge rent to the household that sells. That asymmetry flatters selling and should be fixed before the recommendation is taken seriously.
  3. A one-file HTML export. So the briefing sheet can be emailed without a website.
  4. A "what changed since last build" diff. If the model is re-run annually, the household needs to see what moved, not just where it landed.
  5. Paper-friendly stylesheet. Started — the briefing sheet prints on one page — but the projection tables do not.
  6. A printable decision record. Filled-in, signed, dated, filed with the trust documents. The template exists; the workflow does not.

Review workflow

Accepting a suggestion

  1. Pick an ID. Add a row to COORDINATION.md with a file scope that does not overlap another open claim.
  2. If it is a data change, edit data/facts.json only. Never edit a generated page — it is overwritten on the next build.
  3. If it is a model change, edit model/ only, and record the effect on the headline in COORDINATION.md. A model change that moves the recommendation must be called out.
  4. Rebuild (python3 sitegen.py), run the link check (python3 tools/check_site.py), and confirm no flagged item disappeared silently.
  5. Mark the task needs review, not done. Someone other than the author reads it.

Rejecting a suggestion

Write why, in the same row. A rejected suggestion with a reason is more valuable than a deleted one, because the next reader will have the same idea.

This is a decision-support model, not legal, tax or investment advice. Every figure traces to a verified authority or an explicit assumption. Unverified items are on Flagged for review. Confirm everything with a California estate attorney, a CPA, and a fee-only fiduciary adviser before acting.
